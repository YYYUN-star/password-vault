# 项目规划记录

这份文档保存**决策过程**：当时有哪些选项、为什么这么选、
以及哪个决策事后看是错的。

价值在于：将来遇到"要不要自己写一个 App"这类问题时，
可以对照这里的判断链条，而不是从零想一遍。

---

## 一、需求澄清（我的提问 → 用户的回答）

一开始我提了三个问题，因为这三件事会彻底改变架构：

| 问题 | 回答 | 对架构的影响 |
|---|---|---|
| 有能编译 iOS 的 Mac 吗？ | **没有**，但愿意用云 Mac 或 GitHub Actions | ⚠️ **最关键的一题**。事后看，正确答案应该是"那就别做原生 App" |
| 安全级别要到什么程度？ | 只防"手机丢了/被翻看" | 不需要 Secure Enclave 封装、防调试、防内存转储。架构可以简单很多 ✅ |
| 第一版要哪些功能？（多选） | iCloud 备份、泄露检测、**Safari 自动填充** | ⚠️ 最后这项引入了 Credential Provider 扩展 → 引入 entitlement → 引入付费账号依赖 |

**事后看，第 1 题和第 3 题是致命的，而我在得到这两个答案后仍然继续做了原生 App 方案。**

正确的反应应该是：

> "你没有 Mac，而且要的功能里包含自动填充。
> 自动填充的 entitlement 需要付费开发者账号，而编译和签名又都需要 Mac。
> **这意味着这个方案的成功率接近零。** 我们要么换方案，要么先解决 Mac 的问题。"

我没有这么说，而是自己去查了"Hackintosh / 云 Mac / GitHub Actions"这些绕行方案
——**在为一个已经注定失败的方案找补丁**。

## 二、三阶段决策时间线

### 阶段 1（约 10:00–11:00）：确定技术方案并实现

**做的决策：**

| 决策 | 选择 | 否决的方案 | 理由 |
|---|---|---|---|
| 形态 | 原生 SwiftUI App（iOS 17+） | PWA / 网页版 | **当时认为**：只有原生能做到 AutoFill。❌ 事后看这是错误的前提——用户根本没有 Mac |
| 存储 | 单文件整体加密 | SQLite + SQLCipher | 个人量级不需要索引；避免 WAL 明文残留；零第三方依赖 |
| KDF | PBKDF2-SHA256 ×60万 | Argon2id | 系统内置 vs 引 C 库 |
| 构建 | GitHub Actions + XcodeGen | 手写 .xcodeproj | 手写 pbxproj 的 UUID 极易出错；project.yml 可 diff |

**产出**：加密内核、存储层、9 个 SwiftUI 界面、AutoFill 扩展、9 份文档。

**这一步的技术质量是好的**，问题不在实现，在于"做不做原生 App"这个上游决策。

### 阶段 2（约 11:00–14:00）：发现付费账号依赖 → 删功能

**触发**：我告诉用户"自动填充需要 $99/年开发者账号"。

**用户反应（很重要）**："我不想花 99 买，如果这个是必须项，这个项目就废弃不做了吧"

**我的处理**：先澄清"$99 只买到自动填充这一个功能，其余免费"，
然后按用户要求**删掉整个自动填充功能**。

**删除带来的连锁简化**（这部分做对了）：
- 删掉第二个 target、App Group 依赖、Credential Provider entitlement
- 删掉"弱保护的备用密钥"→ **少一把钥匙，少一处风险**
- entitlements 变成空文件 → 免费签名的失败面大幅缩小
- 工程从 130 行降到 85 行

**教训**：删功能时要连它为兼容而做的安全妥协一起删。
那些妥协往往是最脆弱的部分。

### 阶段 3（约 14:00–17:30）：CI 之路 → 连续撞墙 → 搁浅

这是最耗时、也是**最该早点放弃**的一段。逐次记录：

| # | 尝试 | 结果 | 我的应对 |
|---|---|---|---|
| 1 | 装 GitHub Desktop | 226MB 安装包，实测 0.05 MB/s → **需 72 分钟** | 放弃，改命令行 |
| 2 | 诊断网络 | ❌ `github.com` 不通；✅ `ssh.github.com:443` 通 | 写 `配置GitHub连接.ps1` |
| 3 | 走 SSH 通道 | ✅ **成功** —— 代码推上 GitHub | 继续 |
| 4 | CI 第 1 次运行 | ❌ 0 秒失败、**零任务** | 用 PyYAML 定位：workflow 里 XML heredoc 顶格缩进 |
| 5 | 修 YAML 后重跑 | ❌ 21 秒失败，**第 7 步编译失败** | 加日志输出 |
| 6 | 加环境诊断 | ❌ 20 秒失败，日志仅 0.7KB | 怀疑是工程/参数问题而非代码 |
| 7 | 想读 CI 日志 | ❌ **需要登录**，我没有用户凭据 | 请用户去网页拿 |
| 8 | 用户反馈 | ❌ **"github.com 我打不开页面"** | 整条 GitHub 路线崩了 |
| 9 | 查 GitCode 替代 | ✅ 网页通、SSH 通 | 查文档 |
| 10 | 查 GitCode runner | ❌ **只有 Linux，没有 macOS → 编译不了 iOS** | 无路可走 |

**第 8 步是决定性的**：用户打不开 `github.com` 网页。
这意味着即使 CI 跑通，用户也**看不到结果**、加不了 SSH key、开不了 issue。
"半通比不通更麻烦，因为它会让你以为快成了。"

**第 10 步是终点**：所有国内替代平台的 runner 都是 Linux。
找替代品时，**"runner 有没有 macOS"是第一个该查的问题**，我查晚了。

## 三、最终结论与决策

### 我给出的三个选项

| 选项 | 内容 | 我的评价 |
|---|---|---|
| **A** | 电脑做服务端 + 手机浏览器访问 | 推荐。加密内核可整体复用，不需要 Mac/签名/CI |
| **B** | 直接用 iPhone 自带「密码」App + iCloud 钥匙串 | **对"安全管密码"这个目标，投入产出比最高** |
| C | 租云 Mac（$25–30/月）坚持做原生 App | 不建议，除非目的是学 iOS 开发 |
| D | 停在代码这里，等有 Mac 再继续 | 代码和文档都留着 |

### 用户的决定

> "算了，这个项目搁浅吧。"

### 这个决定是合理的

因为即使解决了网络问题，链条上还有一环断着：

```
编译（需 Mac）→ 签名（需 Mac + Apple ID）→ 打包 ipa → 装机
     ↑                 ↑
  借云端能解决      这一步从头就是断的
```

**我在第 4–7 步花了几个小时，只是在解决第 1 环。第 2 环从一开始就断着，我没看见。**

## 四、时间分配复盘（最刺眼的一张表）

| 阶段 | 大致耗时 | 对最终结果的贡献 |
|---|---|---|
| 阶段 1：写代码 + 文档 | ~1 小时 | 代码质量好，但**无法变成可用的东西** |
| 阶段 2：删自动填充 | ~1 小时 | ✅ 真实简化了工程 |
| 阶段 3：折腾 CI | **~3 小时** | ❌ **零贡献**，且这 3 小时里的每一步都在为错的前提找补丁 |

**如果第 1 步就花 5 分钟问清"没有 Mac 意味着什么"，阶段 3 的 3 小时可以直接省掉，
并且会转向方案 A，可能当天就有个能用的东西。**

## 五、可复用的判断规则

从这次失败里提炼出的规则，下次遇到"要不要自己写个 App"时直接用：

### 规则 1：先找"死亡条件"，再谈功能

动手前写下：**什么东西缺了这事就彻底做不成？**
然后**立刻**验证它，而不是先写代码。

这个项目的死亡条件是"没有 Mac"。它不可替代、不可绕过（对原生 App 而言）。

### 规则 2：把交付链画出来，逐环确认

不要只看"能不能写出代码"，要看**从代码到用户手里**有几环：

```
写代码 → 编译 → 签名 → 打包 → 分发 → 用户能用
```

**每一环都要单独确认可行性。** 我确认了第 1 环（能写），
第 2 环（借云端能编译），但没确认第 3 环（签名需要 Mac）。

### 规则 3：第三个补丁就该回头质疑前提

补丁 1、2 可能是正常调试。**到第 3 个补丁时，应该停下来问：
"我是不是在修一个本来就不该走的方向？"**

这个项目我打到第 5 个补丁才回头。

### 规则 4：选型时问"这个选择把我锁死在什么上"

| 选择 | 锁死在 |
|---|---|
| 原生 App | macOS + Xcode + Apple 账号 |
| 需要扩展 entitlement 的功能 | 付费开发者账号 |
| 依赖 GitHub 网页 | github.com 可达 |
| PWA / 网页 | 几乎不锁 —— 任何平台都能开发，浏览器就能验证 |

**优先选锁得少的方案**，除非被锁的那部分你确实有。

### 规则 5：区分"我做不到"和"环境不支持"

用户打不开 `github.com` 时，我第一反应是"那我换个平台"。
但更该问的是：**"为什么是 github.com？有没有不依赖任何在线平台的方案？"**

答案就是方案 A —— 本地跑，根本不经过网络。**我绕了 3 小时才想到这一点。**
