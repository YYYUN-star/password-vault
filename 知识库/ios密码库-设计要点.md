## 一、加密方案（这部分是对的，可以整体复用）

### 整体结构

```
主密码
  │
  ├─ PBKDF2-HMAC-SHA256 × 600,000 + 32 字节随机盐
  │                                   ↓
  │                              主密钥（32 字节）
  │                                   │
  │        ┌──────────────────────────┼──────────────────────────┐
  │        ↓                          ↓                          ↓
  │   HKDF(info=                  HKDF(info=                 （未来给
  │   "vault-content-v1")         "verifier-v1")              其他用途）
  │        ↓                          ↓
  │   内容密钥                     HMAC 校验值
  │   （加密库文件）               （用来区分"密码错"和"文件坏"）
  └─→ AES-256-GCM（AAD = 文件头原始字节）
```

### 为什么每个选择是这样

| 选择 | 被否决的方案 | 理由 |
|---|---|---|
| **PBKDF2-SHA256 ×60万** | Argon2id | Argon2id 抗 GPU 更强，但 iOS 系统**没有内置实现**，引第三方 C 库会显著增加构建复杂度和供应链风险。文件头保留了算法标识位，将来可无损升级 |
| **AES-256-GCM** | AES-CBC + HMAC | GCM 是 AEAD，一次操作同时保证机密性和完整性。用 CBC 就要自己拼"加密再算 MAC"，那是自创密码学的经典入口 |
| **文件头作为 AAD** | 头部不参与认证 | 头部字段（迭代次数、盐）不加密是必然的（解密前要用）。但如果不认证，攻击者能改迭代次数做降级。把头部字节喂给 AAD，改一个字节就解密失败 |
| **HKDF 分离子密钥** | 内容密钥直接用主密钥 | 一旦将来需要第二把密钥（给备份、给同步），复用主密钥会让两处密文共享密钥，一处泄露即全泄露。HKDF 让不同用途的密钥密码学独立，成本几乎为零 |
| **单独的校验值** | 靠 AEAD 解密失败判断 | AES-GCM 只说"认证失败"，**不区分"密钥错"还是"密文被改"**。想要给用户一句人话提示，就得额外存一段校验值 |
| **`SecRandomCopyBytes`，失败直接崩** | 退化成伪随机 | 熵池故障时"优雅降级"等于静默把所有密码变成可预测的。**崩溃比生成弱密码安全** |
| **拒绝采样的密码生成** | `randomByte % alphabet.count` | 当字符集大小不整除 256 时（如 62），取模会让前面的字符被过度表示。密码生成器的全部价值就在于分布均匀 |
| **符号集排除 `"` `'` `` ` `` `\`** | 全字符集 | 这些字符在某些网站输入框、CLI、配置文件里需要转义，会导致"密码明明复制对了却登录失败"这类极难排查的问题。损失约 4 bit 熵，换来可靠性 |

### 文件格式（自我描述 + 向前兼容）

密码库文件是**要存十年的东西**，一个只能被当前版本读的格式等于给自己埋雷。

```
┌──────────────────────────────────────┐
│ MAGIC      "PWVLT1\0\0"     8 字节    │
│ VERSION    UInt16 BE        2 字节    │
│ HEADER_LEN UInt32 BE        4 字节    │
│ TLV 字段：                            │
│   0x01 KDF_ALGO    1 字节             │
│   0x02 KDF_ITER    UInt32             │
│   0x03 SALT        16..64 字节        │
│   0x04 VAULT_ID    16 字节            │
│   0x7F RESERVED    任意（解析时跳过） │
├──────────────────────────────────────┤
│ BODY  nonce‖ciphertext‖tag           │  ← AAD = 上面全部字节
└──────────────────────────────────────┘
```

**为什么用 TLV 而不是 Codable JSON**：加字段时老版本能"跳过未知字段继续读"，
而不是解码失败。JSON 也能做，但二进制没有编码歧义。

**JSON 编码必须用 `.sortedKeys`**：如果同一份数据两次编码产生不同字节，
"内容没变就不重写文件"的判断会失效。

## 二、密钥链：两个条目 → 一个条目

### 曾经的设计（v0.1，为 AutoFill 扩展服务）

| 条目 | 保护等级 | 用途 |
|---|---|---|
| `vault.masterkey.v1` | `biometryCurrentSet` | 主 App 每次解锁要人脸 |
| `vault.unlockseed.v1` | `devicePasscode` | 扩展后台静默读取 |

**为什么需要两份**：扩展是**后台**被唤醒的独立进程，弹不出人脸面板。
如果条目要求生物识别，扩展只会拿到 `errSecInteractionNotAllowed`，自动填充彻底不可用。
这是 Apple 平台的固有限制，不是偷懒。

**补偿措施**（当时想清楚的）：
- 扩展**只有读权限**，改密码/删条目/导备份只能在主 App 做（每次都人脸）；
- 弱保护的备用密钥仍然是 `ThisDeviceOnly`（不同步、不出设备）；
- 用户可一键关闭整个通道。

### v0.2 的简化

自动填充功能因"需要付费开发者账号"被删除后，**弱保护的副本没有存在理由了**，
直接删掉：**少一把钥匙，少一处风险**。

> **这里有个可迁移的教训**：当你删掉一个功能时，
> 顺手把它为兼容而做的安全妥协也删掉。那些妥协往往是最脆弱的部分。

### Keychain 的三个硬约束

```swift
kSecAttrAccessibleWhenUnlockedThisDeviceOnly   // 锁屏读不出 + 不随 iCloud 同步
.biometryCurrentSet                            // 换脸/换指纹后密钥自动失效
// 主密码永远有效，且不依赖 Keychain —— 密钥没了就重新输主密码
```

**`.biometryCurrentSet` 的含义值得单独说**：它只认"当前录入的"生物特征。
这带来一个真实后果：**用户新增或删除一张脸之后，那个条目会被系统作废**。
如果某个功能依赖它，就必须在 App 侧做自愈，否则会制造一个
"开关看起来开着、但永远不生效"的死锁（扩展是另一个进程，无权改这个开关）。

## 三、存储层的关键决策

### 为什么用单文件整体加密，而不是 SQLite

| 理由 | 说明 |
|---|---|
| 量级匹配 | 个人库几百条，全量解密 + 重编码 < 30ms |
| 泄露形态可控 | 整库单文件意味着泄露只会整体发生，不存在"某个索引页明文残留" |
| 无中间文件 | SQLite 的 WAL/journal 会在磁盘上留下部分明文的影子副本 |
| 零依赖 | SQLCipher 是 C 库，GRDB 是外部包 |

代价：每次保存重写整个文件。对几百 KB 完全可接受。

### 变更检测：内容没变就不写盘

```swift
if let last = lastSavedPlaintext, Data.constantTimeEquals(last, plaintext) {
    state = .unlocked(unlockedState)
    return           // 不写
}
```

不是为了微优化，而是：减少闪存磨损，更重要的是**避免给未来的同步制造假冲突**。

### `@MainActor` 强制串行

加密库的读写交错是 bug 温床（保存过程中用户又改了一条 → 旧快照覆盖新数据）。
强制串行在 UI 线程换来的确定性，远比那几十毫秒的异步收益重要。

## 四、恢复流程的强制约束

> **必须先用该备份的主密码成功解密一次，才允许写入。**

顺序不能反。否则用户手滑导入一个不相干的文件，就会把现有库永久覆盖。

```swift
let plaintext = try CryptoBox.open(...)      // 失败就抛错，此时什么都没写
let payload = try VaultFile.decodePayload(plaintext)
try writeAtomically(data)                    // 到这里才第一次碰磁盘
```

**这也是"恢复"这个操作唯一安全的实现形态**：
先完整验证 → 再整体替换。中途崩溃不会留下半截文件。

## 五、隐私相关的设计（容易被忽略但很重要）

| 决策 | 理由 |
|---|---|
| **不抓网站 favicon** | 抓图标需要向第三方服务器发请求，会**实时暴露"我在用哪些网站"**。密码管理器最不该做的就是主动往外发请求。用字母图标代替 |
| **泄露检测用 k-匿名** | 只发密码 SHA-1 的**前 5 位**给 HIBP，本地比对返回的约 1000 条候选。服务端无法反推具体密码 |
| **泄露检测默认关闭** | 这条请求本身会暴露 IP。只在你主动点击时才发 |
| **查询失败必须区别于"未泄露"** | 三态结果 `found / notFound / unknown`。**把网络错误显示成"安全"是最危险的实现方式** |
| **防截屏遮罩用不透明层，不用模糊** | iOS 切后台时会拍快照存到磁盘，即使 App 被杀也还在。模糊在某些渲染时序下会把内容糊进快照 |
| **日志出口在 Release 完全编译掉** | `#if DEBUG` 包住。密码管理器里"随手 print 调试"是灾难的开始 |
| **错误文案里不放任何库内信息** | 例如人脸弹窗文案是"解锁密码库"，不是"给 github.com 解锁"——后者会让锁屏上出现你的账号信息 |

### 域名匹配必须保守

```swift
// 只认精确相等或互为子域
h == target || h.hasSuffix("." + target) || target.hasSuffix("." + h)
```

**绝不引入模糊匹配或编辑距离**。那会让 `evil-github.com` 也匹配到你的
github 密码。密码管理器里，**"少给一条候选"永远优于"给错一条候选"**。

## 六、待办（如果有 Mac 之后继续）

按价值排序：

1. **先跑通编译**（从未被真正的苹果编译器检查过，这是第一件事）
2. 单元测试：`CryptoBox`（PBKDF2 已知向量）、`VaultFile`（往返编解码）、
   `PasswordGenerator`（分布均匀性）—— 这三块是纯函数，最好测
3. 真机验证 Face ID / Keychain 行为（模拟器上生物识别是假的）
4. 性能基准：确认 60 万次 PBKDF2 在目标机型上的实际耗时
5. 若要加自动填充：见 `../docs/PAID_FEATURES.md`（含 3 个已验证的坑）

## 七、已知未做的事

| 项 | 说明 |
|---|---|
| 多设备实时同步 | 只有加密备份/恢复。CloudKit 记录级合并会引入冲突、墓碑、时钟偏移，做错会静默丢数据 |
| 内存清零 | Swift 没有 `mlock`/`explicit_bzero` 的可靠等价物。只能尽早断开强引用。这是 Swift 的固有限制 |
| 元数据保护 | 文件名、大小、条目数都不加密。对个人使用场景不值得 |
| TOTP 两步验证码 | 未实现。注意：把第二因素和密码放一起是安全性降级 |
