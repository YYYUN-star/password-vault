# 经验教训：一次失败项目的完整复盘

**项目**：iOS 密码管理器（PasswordVault）
**时间**：2026-10-11，单日完成
**结果**：代码完成（3000+ 行 Swift），但**项目搁浅** —— 无法编译、签名、安装到 iPhone
**根本原因**：没有 Mac，且此前提在写代码之前未被验证

---

## 一、最重要的一条教训

> **先验证那个"不可逆、不可替代"的前提，再写第一行代码。**

这个项目里，唯一不可替代的前提是：**要有一台 Mac**。
它不满足 → 整个方案在架构上就是死的 → 后面所有补丁都是徒劳。

我犯的错是这样的：

| 顺序 | 我做的事 | 应该做的事 |
|---|---|---|
| 1 | 直接开始写 3000 行 Swift | ✋ **先问："你有 Mac 吗？"** |
| 2 | 第二轮才知道没有 Mac | 此时架构已定死（原生 App + 扩展 entitlement） |
| 3 | 引 GitHub Actions 当"云端 Mac" | 这只是补丁，救不了错的前提 |
| 4 | 每撞一堵墙就打一个补丁 | 应该说："这条路对没有 Mac 的人是死的，换方案" |

**补丁救不了错的前提。** 打第三个补丁的时候就该回头质疑前提，我打到第五个才回头。

### 可复用的检查清单

动手前先写下这个项目的"死亡条件"，然后**立刻**去验证：

1. 有什么东西是**买不到、借不到就做不成**的？（硬件、账号、付费能力）
2. 有什么东西是**不可逆**的？（选了原生 App，就绑定了 Mac + 签名）
3. 有什么东西是**我以为对方有、但没确认过**的？（Mac、代理、信用卡）
4. 这些前提下，**最终交付物长什么样**？用户拿到手里能干什么？

第 4 条尤其重要。这个项目的交付物是"能装到 iPhone 上的 App"，
而这条链上有 **4 个环节**，我只解决了第 1 个就以为快成了：

```
编译 (需 Mac)  →  签名 (需 Mac + Apple ID)  →  打包 ipa  →  装机
     ↑ 我在这花了 4 轮              ↑ 这一步从一开始就是断的，我没看见
```

## 二、技术教训（都是踩出来的，带最小示例）

### 1. PowerShell 5.1 在中文 Windows 上读无 BOM 的 UTF-8 脚本会按 GBK 解码

**症状**：报"语法错误"，位置指向一行看起来完全正常的代码。

**真因**：中文被按 GBK 解码成乱码，乱码字节里混进引号，把字符串截断了。

```powershell
# 无 BOM 的 UTF-8 文件里写了这句话：
Write-Host '请输入你的名字'
# PS 5.1 按 GBK 解码后变成乱码，其中的某个字节被当成引号 → 字符串提前结束
# 报错：字符串缺少终止符: "
```

**两个修法**：

- 存成 **UTF-8 with BOM**（但任何一次编辑都可能丢掉 BOM，很脆）
- ✅ **更稳的：整个脚本只用 ASCII**，中文全部编码后运行时解码

```powershell
# 把中文按 Unicode 码点写成十六进制 —— 纯 ASCII，任何代码页下都能正确解析
$M = @{
    'ask' = '8BF78F9351654F60'   # "请输入"
}
function Get-Msg([string]$key) {
    $hex = $M[$key]
    $sb = New-Object System.Text.StringBuilder
    for ($i = 0; $i + 4 -le $hex.Length; $i += 4) {
        [void]$sb.Append([char][System.Convert]::ToInt32($hex.Substring($i, 4), 16))
    }
    return $sb.ToString()
}
```

> ⚠️ **连注释里都不能有中文。** 我在这上面栽过：中文放在行尾注释里，
> 乱码照样把后面的引号吃掉，照样解析失败。

**验证方法**（写成硬规矩）：

```powershell
$b = [System.IO.File]::ReadAllBytes($script)
$n = ($b | Where-Object { $_ -gt 127 } | Measure-Object).Count
if ($n -ne 0) { throw "脚本里有 $n 个非 ASCII 字节，会有编码风险" }
```

### 2. `$ErrorActionPreference = 'Stop'` 会把原生命令的 stderr 当成致命错误

**症状**：脚本在完全正常的命令处中断。

**真因**：`ssh -V`、`ssh-keyscan`、`git` 这些原生命令**成功时也往 stderr 写东西**。

```
ssh -V         → 版本号写在 stderr
ssh-keyscan    → 横幅 "# host:port SSH-2.0-xxx" 写在 stderr
```

**修法**：不要逐个命令打补丁（我打了 4 次补丁才醒悟），统一包一层：

```powershell
function Invoke-Native {
    param([string]$Exe, [string[]]$Arguments = @())
    $prev = $ErrorActionPreference
    try {
        $ErrorActionPreference = 'Continue'
        $result = @(& $Exe @Arguments 2>&1)
    } catch {
        $result = @($_.Exception.Message)
    } finally {
        $ErrorActionPreference = $prev
    }
    return @($result | ForEach-Object { $_.ToString() })
}
```

并把脚本开头的 `Stop` 改成 `Continue` —— 每一步用**显式检查**判断成败
（文件是否存在、输出内容是否匹配），比依赖异常终止更可靠。

### 3. `git config` 的引号行为（实测，不是猜的）

设置 `core.sshCommand` 时踩到的坑。**这个 bug 只在真正发起 git 远端操作时才现形**，
`ssh -T` 测不出来（它走的是 `~/.ssh/config`）。

| 你存进去的值 | 读回来的值 | 后果 |
|---|---|---|
| `C:/Program Files/x/ssh.exe` | 同左 | git 在空格处截断 → `C:/Program: No such file` |
| `"C:/Program Files/x/ssh.exe"` | `C:/Program Files/x/ssh.exe` | **外层引号被吃掉** → 同样失败 |
| `\"C:/Program Files/x/ssh.exe\"` | `"C:/Program Files/x/ssh.exe"` | ✅ 引号保留 |
| `C:/PROGRA~1/x/ssh.exe` | 同左 | ✅ **无空格，根本不需要引号（首选）** |

**结论**：优先用 8.3 短路径避开空格，而不是去跟引号转义搏斗。

```powershell
$fso = New-Object -ComObject Scripting.FileSystemObject
$short = $fso.GetFile($exePath).ShortPath     # C:\PROGRA~1\...
```

而且**必须读回校验 + 功能验证**，不能只看"看起来设对了"：

```powershell
$stored = Invoke-Native git @('config','--global','core.sshCommand')
$test   = Invoke-Native git @('ls-remote','--heads','git@github.com:github/gitignore.git')
if (($test -join ' ') -match 'No such file|Could not fork') { throw "配置不可用" }
```

### 4. GitHub Actions 的 workflow 文件被拒时，表现是"零任务、0 秒失败"

**症状**：`gh run view` 显示 completed/failure，但 `jobs` 是空的，
开始时间和结束时间是同一秒。

**含义**：**workflow 文件本身非法**，GitHub 连 job 都没创建。
这和"代码编译失败"是完全不同的两类问题，不要混。

**我犯的具体错误**——在 `run: |` 块标量里嵌 XML heredoc，内容顶格写在第 0 列：

```yaml
        run: |
          cat > out.plist <<PLIST
<?xml version="1.0"?>          # ← 第 0 列！YAML 认为块标量在此结束
</plist>
PLIST
```

于是 XML 被当作 YAML 语法解析 → `ScannerError: could not find expected ':'`。

**正确写法**：内容全部缩进到块标量内部：

```yaml
        run: |
          cat > out.plist <<PLIST
          <?xml version="1.0"?>
          </plist>
          PLIST
```

**顺带发现的第二个坑**：`<<PLIST` 后面**必须换行**。
写成 `<<PLIST` 紧跟内容在同一行，bash 会认为 heredoc 立即结束，
**生成一个 0 字节的空文件**，而且不报任何错。

**验证方法**：本地用 PyYAML + bash 双重校验，不要推到 CI 才知道错。

```python
import yaml
yaml.safe_load(open("build.yml", encoding="utf-8"))   # 抓 YAML 结构错误
```
```bash
bash -n <(提取出的 run 块)                              # 抓 shell 语法错误
```

### 5. GitCode（gitcode.com）的 runner 只有 Linux

查证结果（2026-10）：

| 项 | 结论 |
|---|---|
| runner 操作系统 | `ubuntu-latest`、`euler-latest` —— **没有 macOS** |
| workflow 位置 | `.gitcode/workflows/` |
| 语法 | 与 GitHub Actions 类似（`on` / `jobs` / `runs-on` / `steps`） |
| 开启方式 | **需要联系客服申请开通**代码化流水线 |

**结论**：GitCode 不能编译 iOS。找国内替代品时，**先确认 runner 有没有 macOS**，
这是第一个该查的问题。

### 6. 浏览器的 Web Crypto 只在"安全上下文"可用

```
https://...        → ✅ crypto.subtle 可用
http://localhost   → ✅ 可用
http://192.168.x.x → ❌ 不是安全上下文，crypto.subtle 不可用
```

**推论**：手机通过 `http://<电脑IP>` 访问的方案里，
**密码学核心必须放在电脑侧**（Python 等），浏览器只当界面。
这反而是好事：核心更可控、更好审计。

### 7. 中国大陆网络下 GitHub 的真实可用性（实测）

| 域名 | 结果 |
|---|---|
| `github.com` | ❌ TCP 443 超时（SNI 阻断），**浏览器也打不开** |
| `ssh.github.com:443` | ✅ **通** —— GitHub 官方的备用 git 通道 |
| `desktop.githubusercontent.com` | ✅ 通（226MB 安装包实测 0.05 MB/s，要 72 分钟） |
| `api.github.com` | ✅ 通（但 Actions 日志/artifact 下载需登录） |
| `gitcode.com` / `gitee.com` | ✅ 通 |

**可用的绕行方案**：走 `ssh.github.com:443` 推送。

```sshconfig
# ~/.ssh/config
Host github.com
    HostName ssh.github.com
    Port 443
    User git
    IdentityFile ~/.ssh/id_ed25519_github
    IdentitiesOnly yes
```

**但要注意**：这只解决了"推代码"。网页看不了 → Actions 结果看不了、
issue 开不了、SSH key 也加不了。**半通比不通更麻烦，因为它会让你以为快成了。**

### 8. Windows 自带 OpenSSH 太老，连不上 GitHub

## 三、做对的地方

失败的项目也有值得留下的东西：

1. **加密内核的设计是对的**（见 `../知识库/ios密码库-设计要点.md`）
   —— AES-256-GCM、PBKDF2 60 万次、文件头作为 AAD、HKDF 分离用途子密钥、
   拒绝采样的密码生成器（无取模偏差）。这些不依赖平台，都是对的。

2. **安全边界想清楚了并写进文档**，而不是假装两全
   —— 例如"忘记主密码就永久无法恢复"这件事，
   在创建流程里做成强制确认，而不是藏在"我同意"里。

3. **SSH 通道方案真的解决了**
   —— 代码确实推上 GitHub 了，这一步是成功的。

4. **测试习惯是对的**：每个脚本都在沙箱里实测（`$env:USERPROFILE` 指向临时目录），
   并对比测试前后真实 `~/.ssh`、`~/.gitconfig` 的哈希，确认没有污染用户环境。
   这条习惯抓住了好几个真 bug。

5. **被删除的功能也记录下来了**
   —— 自动填充功能（需要付费开发者账号）删除时，
   把它踩过的坑写进了 `docs/PAID_FEATURES.md`，而不是一删了之。

## 四、如果重来一次

**同样的需求（自己用的密码管理器）+ 同样的约束（Windows、无 Mac、无付费账号），我会这样做：**

**第一步（5 分钟，不写代码）**：确认交付物和死亡条件。

> "能做出来的最好东西是：手机浏览器打开的网页，加密算法跑在你电脑上，
> 手机连着家里 WiFi 就能用。**没有 Mac 的话，原生 App 是不可能的。**
> 你要这个，还是用 iPhone 自带的密码 App？"

**第二步**：如果选网页方案，在 Windows 上直接写、直接测、直接看结果，
**一轮就能跑通**，不需要 GitHub、不需要 CI、不需要签名。

**第三步**：如果用户坚持要原生 App，那就是"先借一台 Mac"作为前置任务，
而不是"先写 3000 行代码再说"。
